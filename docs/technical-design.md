## 1. Purpose and authority

This is the implementation contract for **Neolab.ai**. It should let a developer construct the simulation, content pipeline, browser interface, saves, and test harness without making new architectural decisions in the middle of feature work.

When the documents disagree:

1. The Game Design Document is authoritative about game behaviour, balance intent, copy, and player experience.
2. This document is authoritative about code boundaries, data ownership, APIs, deterministic execution, persistence, and extension mechanisms.
3. A numerical balance constant belongs in content/balance data even when it appears in either document.
4. A contradiction must be resolved in the documents before code is changed to “pick one.”

The signatures in this document are normative API shapes but not production source files. Small naming improvements are allowed during implementation if the same boundaries and guarantees remain intact.

## 2. Engineering goals and non-goals

### 2.1 Goals

- Reproduce a run exactly from seed, initial configuration, content version, and command log.
- Run the complete simulation without React, a browser, timers, sound, or graphics.
- Make events, papers, researchers, leaders, facilities, offers, and most modifiers addable as validated content.
- Prevent UI code from reading hidden safety truth accidentally.
- Keep save files plain, versioned data rather than serialised class instances.
- Make one weekly tick atomic, ordered, testable, and explainable.
- Support tens of thousands of headless balance runs.
- Keep the first public build entirely static and playable offline after load.
- Permit a future sixth lab, new research domain, new event category, or additional endgame route without a rewrite.
- Give content errors precise file paths and human-readable messages before the game launches.
- Maintain keyboard, screen-reader, colour, and reduced-motion accessibility from the first vertical slice.

### 2.2 Non-goals for version one

- Multiplayer or authoritative server simulation
- Live-service economy
- User accounts, cloud saves, or required telemetry
- Procedural prose generated by a remote AI service
- General third-party executable mods
- Mobile-phone layout
- Physically simulated campus agents
- A generic game engine intended for unrelated games
- Cryptographic secrecy of hidden state from a player inspecting their own browser

### 2.3 Core architectural choice

Use a **functional core with an imperative shell**.

- The functional core is the simulation: typed data in, typed data out, no environmental side effects.
- The imperative shell is the browser runtime: clocks, input, rendering, save storage, file import/export, sound, and optional telemetry.

Do not build an inheritance hierarchy such as `Person extends Entity`, `Researcher extends Person`, or `RivalLab extends Lab`. Entities are plain records with stable IDs. Behaviour lives in focused systems and pure functions. This avoids save-format problems, fragile subclass coupling, and a situation where adding one character requires a new JavaScript class.

Classes are appropriate only for objects with runtime lifecycle or encapsulated adapters, such as `GameRuntime`, `AudioManager`, `IndexedDbSaveRepository`, and an optional `CampusRenderer`. They are not the canonical game state.

## 3. Chosen platform and technology

### 3.1 Required stack

| Concern | Choice | Reason |
|---|---|---|
| Language | TypeScript with all strict checks | Static checking for a large state model and exhaustive command/effect unions |
| UI | React function components | Strong fit for an information-dense dashboard and controlled state flow |
| Build/dev server | Vite | Fast development, static production output, TypeScript/React support |
| UI store | Zustand vanilla store plus React bindings | Small selector-based bridge between runtime views and components |
| Content validation | Zod | Runtime validation and TypeScript inference for authored data and saves |
| Content parsing | `yaml` package in YAML 1.2 mode | Safe, source-located build-time parsing before Zod validation |
| Deterministic key hashing | `@noble/hashes` SHA-256 | Identical synchronous digest in browser and Node balance tools |
| Unit/integration tests | Vitest | Same TypeScript/Vite toolchain and fast headless test execution |
| Browser end-to-end tests | Playwright | Chromium, Firefox, and WebKit coverage with accessible browser automation |
| Styling | CSS Modules plus CSS custom properties | Local component styles without surrendering the visual language to a utility framework |
| Package management | pnpm workspaces via Corepack | Reproducible monorepo installs and clear package boundaries |
| Persistence | IndexedDB behind a repository interface | Reliable local saves larger than basic key/value preferences |
| Content source | YAML compiled to canonical JSON | Author-friendly records with runtime simplicity and schema validation |
| Campus graphics | HTML/CSS initially; PixiJS 8 only if measured need exists | Avoid a rendering engine until sprite count or effects justify one |

Use the current stable releases at project initialisation and commit the lockfile. Do not put floating `latest` ranges in `package.json`. Record Node and pnpm versions in `.tool-versions` or `.nvmrc` plus the `packageManager` field.

### 4.1 Dependency direction

Allowed dependencies are one-way:

```text

content-schema ← content
content-schema ← testkit
sim + compiled content ← testkit
sim + compiled content ← web
testkit + sim + compiled content ← balance-runner
```

Forbidden:

- `sim` importing React, Zustand, browser APIs, PixiJS, or files from `apps/web`
- Authored content importing simulation implementation
- UI components importing internal `sim/src/**` paths instead of `@neolab/sim/public`
- A system directly importing a React selector
- Save adapters writing into simulation state after validation

Enforce public package exports in `package.json` and add an ESLint restricted-import rule.

## 5. Architectural rules

### 5.1 Plain serialisable state

Canonical game state contains only:

- Objects with plain data properties
- Arrays
- Strings
- Booleans
- Finite numbers
- Explicit `null` only where a schema requires it

It contains no `Date`, `Map`, `Set`, class instance, function, DOM node, Promise, Error, typed array, or circular reference. Entity collections use `Record<Id, EntityState>` plus explicit order arrays when order matters.

### 5.2 Definitions versus instances

Immutable content definitions are not copied into saves.

- `ResearcherDefinition` describes Yann LeNet's skills, portrait, traits, and content hooks.
- `ResearcherState` stores current employer, morale, loyalty, burnout, contract, assignment, and flags.
- `EventDefinition` describes trigger and options.
- `EventInstance` stores instantiated tokens, created tick, expiry, committed outcome keys, and resolution.

State references definitions by stable content ID. This keeps saves small and lets copy corrections occur without rewriting every save.

### 5.3 Stable IDs

Use branded strings at compile time:

```ts
type Brand<T, B extends string> = T & { readonly __brand: B };

type LabId = Brand<string, "LabId">;
type ModelId = Brand<string, "ModelId">;
type ProjectId = Brand<string, "ProjectId">;
type ContentId = Brand<string, "ContentId">;
```

Content IDs are namespaced and never reused:

```text
base:leader.thomas_hassabi
base:lab.deepbrain
base:event.ai.root_access_request
base:paper.attention_is_all_you_need
```

Renaming display copy never changes an ID. A removed ID remains reserved. Content aliases exist only for explicit migration.

### 5.4 Units

Do not pass ambiguous naked values between subsystems. Use branded aliases or field names which include the unit:

```ts
type Tick = Brand<number, "Tick">;
type CashMillions = Brand<number, "CashMillions">;
type GpuCount = Brand<number, "GpuCount">;
type GpuWeeks = Brand<number, "GpuWeeks">;
type Rating = Brand<number, "Rating0To100">;
type Fraction = Brand<number, "Fraction0To1">;
```

Construct them through validating helpers such as `rating(value)` and `fraction(value)`. Ratings clamp only where the game rule says to clamp; invalid programmer input should fail an invariant rather than disappear silently.

### 5.5 Derived state

Do not store values which can be cheaply and unambiguously derived:

- Store cash, income contracts, and expenses; derive projected net and runway.
- Store physical GPU lots by generation plus availability; derive training or serving throughput when a rule needs it. Derived throughput is never stored as owned hardware and never exposed as `CU`.
- Store capability vector; derive FC.
- Store Lifetime Aura and event history; derive Aura Signal.
- Store hidden truth and observations; derive the player safety view.

If a derived value becomes expensive, cache it outside the save with explicit invalidation. Never allow two canonical sources of truth.

### 5.6 Exhaustive unions

Commands, effects, project kinds, event resolution states, ending states, and major notices are discriminated unions. Switches in the simulation must end with an `assertNever` branch so that adding a variant creates compilation failures at every unhandled site.

## 6. Runtime lifecycle

### 6.1 Browser boot

The web app boots in this order:

1. Load settings and accessibility preferences.
2. Load and validate the compiled content manifest.
3. Initialise the save repository.
4. Show the title screen.
5. Create a `GameRuntime` only after new-game configuration or save loading succeeds.
6. Project canonical state into a player-safe `GameView`.
7. Publish the view to the Zustand bridge store.
8. Start the real-time clock only when the run is unpaused.

Content validation failure is a fatal development error and a readable release error with the content version. A corrupt save must not prevent the title screen opening.

### 6.2 GameRuntime

`GameRuntime` is the imperative boundary and the only normal owner of canonical state in the browser.

```ts
interface GameRuntime {
  getView(): GameView;
  getClock(): ClockView;
  subscribe(listener: RuntimeListener): Unsubscribe;
  dispatch(command: GameCommand): CommandReceipt;
  setSpeed(speed: ClockSpeed): void;
  pause(reason?: ManualPauseReason): void;
  resume(): ResumeResult;
  stepOneTick(): TickReceipt;
  exportSave(options?: ExportOptions): Promise<Blob>;
  dispose(): void;
}
```

The concrete class owns:

- Canonical `GameState`
- Validated `CompiledContent`
- Clock accumulator and selected speed
- Command and tick serialization queue
- View-projection cache
- Autosave scheduling
- Runtime subscribers
- Browser adapters passed through constructor injection

It never contains game formulas. `dispatch` delegates to the simulation package, commits the returned state atomically, then projects and publishes a new view.

### 6.3 Clock

The browser clock uses monotonic elapsed time from `performance.now()`, not `setInterval` as a source of game truth.

```ts
type ClockSpeed = "paused" | "1x" | "2x" | "4x";

interface ClockDriver {
  start(onFrame: (elapsedMs: number) => void): void;
  stop(): void;
}
```

Real milliseconds per tick come from balance data: 4000, 2000, and 1000 by default. The runtime accumulates elapsed time and requests atomic ticks. It processes at most four ticks in one animation frame; remaining debt carries forward. A hidden tab may advance slowly or pause according to settings, but it may not skip simulation steps.

When a tick returns an auto-pause reason, the runtime finishes that tick, publishes the view, stops consuming accumulated time, and opens the highest-priority blocking presentation.

Clock speed, selected tab, animation frame, and open tooltip are not simulation commands and do not affect deterministic replay.


### 7.1 RunState

```ts
interface RunState {
  runId: RunId;
  seed: Seed128;
  difficultyId: ContentId;
  playerLabId: LabId;
  tick: Tick;
  calendar: GameCalendar;
  phase: GamePhase;
  status: "active" | "won" | "lost";

```

IDs for run-created entities use deterministic counters, not random UUIDs. For example, the seventh player model can be `run:model:player:0007`. Real creation timestamps belong only in the save envelope, never in the run state.

### 7.2 LabState slices

`LabState` is composed of named slices rather than one undifferentiated object:

```ts
interface LabState {
  id: LabId;
  definitionId: ContentId;
  control: "player" | "rival";
  finance: FinanceState;
  compute: ComputeState;
  research: ResearchState;
  safety: LabSafetyState;
  organisation: OrganisationState;
  roster: RosterState;
  facilities: FacilityPortfolioState;
  market: MarketState;
  politics: PoliticsState;
  models: LabModelPortfolioState;
  projects: LabProjectIndex;
  strategy?: RivalStrategyState;
  flags: Record<FlagKey, FlagValue>;
}
```

Subsystems receive the full transaction state when cross-system rules require it, but their exported helpers operate on focused inputs. Do not build a `Lab` god class with methods for every mechanic.

`LabModelPortfolioState` separates internal technical leadership from the customer-facing product:

```ts
interface LabModelPortfolioState {
  currentModelId?: ModelId; // active internal model
  commercialModelId?: ModelId; // model used by market/serving
  modelIds: ModelId[];
}
```

A new game has an empty portfolio and an empty global model index. The first parentless training run creates generation zero and sets only `currentModelId`. Successor completion changes `currentModelId` without changing `commercialModelId`; an external deployment command changes the commercial role. Both optional IDs, when present, must reference models owned by the lab and included in `modelIds`. Save version 3 keeps `commercialModelId` optional. A legacy save without it treats an externally deployed current model as commercial until the next explicit deployment command, so no save-version migration is required. This rules change is identified by engine rules version `0.2.0`.

### 7.2.2 Finance state

```ts
interface FinanceState {
  cash: CashMillions;
  ledger: FinanceLedgerEntry[];

  id: string;
  settledAt: Tick;
  settlementId?: string;
```

Recurring entries carry a settlement ID and reconcile exactly against that settlement. Immediate cash movements, such as a GPU purchase or asset sale, use the same ledger categories and source IDs but omit the settlement ID. ### 7.2.3 Market state

```ts
interface MarketState {
  marketShare: Fraction;
  priceTier: PublicPriceTier;
  pendingPriceTier?: PublicPriceTier;
  priceChangeTicks: Tick[];
  monetisationEfficiency: Fraction;

```

Usage is accrued weekly so financial settlement receives exact delivered revenue. The continuous forecast combines accrued actuals with the current-plan estimate for the unelapsed weeks. A pending public price tier is canonical player intent and becomes active only at the next cycle boundary.

### 7.2.4 Facility instances and project payloads

```ts
interface FacilityInstanceState {
  id?: FacilityId; // absent only on migrated save-version-1 records
  definitionId: ContentId;
  completedAt: Tick;
  enabled: boolean;
  majorProjectSlotBonus: number;
  modifierIds: ModifierId[];
}

interface ProjectResourceReservations {
  majorProjectSlots: number;
}

type ProjectPayload =
  | {
      kind: "construction";
      facilityDefinitionId: ContentId;
      upfrontCostMillions: CashMillions;
    }
  | { kind: "training" }
  | { kind: "evaluation" };
```

All newly created facility instances have deterministic IDs. `modifierIds` is the exact source index used to disable and later reconstruct benefits; it is never a list of guessed reverse arithmetic. Project payload kind must match project kind, and active reservation totals may not exceed Major Project capacity — except that crisis projects may run up to the crisis floor (two) beyond a fully committed pool. Facility construction reserves one ordinary Major Project slot; there is no separate construction scheduler.

### 7.3 Hidden state

Hidden model truth, rival plans, research thresholds, event outcome keys, and Internal Candour are present in canonical state. They are stored under clearly named fields such as `model.hiddenSafety`, not mixed with visible estimates.

Only selectors in `sim/src/selectors/knowledge/**` may convert hidden state into player-visible evidence. UI code never imports canonical state types and never receives `GameState` from `GameRuntime`.

Browser users can inspect exported saves if they wish. This is not a security boundary; it is an engineering boundary preventing accidental spoilers in normal play and accessibility output.

## 8. Commands and transactions

### 8.1 GameCommand

All simulation-changing player intent enters through a command:

```ts
type GameCommand =
  | SetGpuAllocationCommand
  | SetResearchFocusCommand
  | StartProjectCommand
  | CancelProjectCommand
  | PurchaseGpuCommand
  | StartConstructionCommand
  | RecruitResearcherCommand
  | DismissResearcherCommand
  | RespondToDecisionEventCommand
  | SetModelDeploymentCommand
  | SetModelAccessCommand
  | ChoosePublicationPolicyCommand
  | AcceptFundingOfferCommand
  | ChooseDeploymentModeCommand
  | ReturnToEvidenceSprintCommand;
```

Each command includes:

```ts
interface CommandMeta {
  commandId: CommandId;
  expectedTick: Tick;
  issuedBy: "player" | "tutorial" | "debug";
}
```

`expectedTick` catches stale confirmations: if time advanced while a non-pausing panel was open, the engine rejects the command and the UI asks the player to review changed costs.

### 8.2 Validation and application

```ts
function validateCommand(
  state: GameState,
  content: CompiledContent,
  command: GameCommand,
): CommandValidation;

function applyCommand(
  state: GameState,
  content: CompiledContent,
  command: GameCommand,
): TransitionResult;
```

`applyCommand` validates again and is atomic. It never partially pays a cost and then returns an error.

```ts
type CommandValidation =
  | { ok: true; preview: CommandPreview }
  | { ok: false; errors: RuleViolation[] };

interface TransitionResult {
  state: GameState;
  domainEvents: DomainEvent[];
  autoPauseReasons: AutoPauseReason[];
  audit: TransitionAudit;
}
```

`CommandPreview` is generated from the same rule functions used by application and includes known cash, compute, time, opportunity cost, reversibility, and visible risk. The UI must not implement its own cost formula.

### 8.3 Immediate versus queued commands

Commands follow the Game Design Document timing rules:

- Allocation, focus, assignment, price, and persistent-policy commands create `QueuedOrder` records for the next tick.
- Decision-event responses, purchases, signed offers, dismissals, publication choices, and deployment confirmations resolve immediately while paused.
- Starting a normal project reserves its slot immediately and begins progress at the next tick.
- A command response can create an auto-pause reason but cannot advance time.

### 8.4 Domain events versus authored events

Use different names for different concepts:

- A `DomainEvent` is an internal fact emitted by the engine, such as `CashSettled`, `PaperDiscovered`, or `ResearcherDeparted`.
- An `EventDefinition` is authored content with player choices.
- An `EventInstanceState` is one occurrence of authored content in a run.
- A `FeedItemView` is presentation derived from domain events or templates.

Domain events are typed and may trigger rules, UI moments, or autosaves. They are not the canonical state; state remains the source of truth.

## 9. Weekly tick engine

### 9.1 Public API

```ts
function advanceOneTick(
  state: GameState,
  content: CompiledContent,
): TransitionResult;
```

No API advances an arbitrary number of weeks by multiplying formulas. Fast-forward is a loop over `advanceOneTick`, preserving events, schedules, and ordering.

### 9.2 Tick phases

### 9.3 SimulationTransaction

The external engine is pure. Internally, one tick may use a transaction object to avoid cloning the complete state after every system:

```ts
interface SimulationTransaction {
  readonly before: Readonly<GameState>;
  read(): Readonly<GameState>;
  update(updater: StateUpdater): void;
  applyEffects(effects: Effect[], source: EffectSource): void;
  emit(event: DomainEvent): void;
  schedule(effect: ScheduledEffectState): void;
  allocateId(namespace: IdNamespace): string;
  commit(): TransitionResult;

```

The concrete transaction owns a working copy or structural-sharing draft which never escapes the call. `commit` runs global invariants and freezes state in development builds. If a system throws, the original state remains unchanged and the runtime pauses with a diagnostic error.

### 9.4 TickContext

```ts
interface TickContext {
  readonly tick: Tick;
  readonly content: CompiledContent;
  readonly random: RandomOracle;
  readonly rules: BalanceRules;
  readonly calendar: GameCalendar;

```

Systems do not call global services. Real time, local storage, sound, network, and UI are unavailable.

### 9.5 Invariants after every command and tick

- All fractions and ratings are finite and in range.
- Allocation at each hierarchy level sums to one within `1e-9`.
- A resource reservation cannot exceed available capacity unless its state explicitly records a shortage.
- Cash and RP never become `NaN` or infinite.
- Entity indexes reference existing entities and correct owners.
- One researcher has at most one employer and one star slot.
- One world-first paper has at most one discoverer.
- Major Project slots are not overfilled, including by facility construction.
- An unresolved blocking event has at least one enabled option.
- Ending status and endgame state are compatible.
- Scheduled effects have a future tick and stable ID.
- No player-facing log payload contains hidden-only fields.

In development and tests, run all invariants. In production, retain low-cost critical invariants and report a recoverable diagnostic before corrupt state can be saved.

## 10. Deterministic randomness

### 10.1 RandomOracle API

No simulation code may call `Math.random`, time, browser entropy, or array shuffling without an injected oracle.

```ts
interface RandomOracle {
  uniform(key: RandomKey): number; // [0, 1)
  integer(key: RandomKey, minInclusive: number, maxInclusive: number): number;
  triangular(
    key: RandomKey,
    min: number,
    mode: number,
    max: number,
  ): number;
  weighted<T extends string>(
    key: RandomKey,
    weights: Readonly<Record<T, number>>,
  ): T;
  shuffle<T>(key: RandomKey, values: readonly T[]): T[];
}
```

`RandomKey` is a structured semantic path, converted to a canonical string:

```ts
const key = randomKey(
  "training",
  modelId,
  "capability",
  "reasoning",
);
```

### 10.2 Algorithm and versioning

Implement and freeze `RandomOracleV1` inside `packages/sim` using SHA-256 and xoshiro128**. It is deterministic infrastructure, not a security mechanism.

For each semantic key:

1. Canonicalise the 128-bit master seed as 32 lower-case hexadecimal characters.
2. Validate that every key segment is non-empty UTF-8 text without ASCII control characters.
3. Encode `neolab-rng-v1`, the seed, and every segment as UTF-8, each preceded by its unsigned 32-bit big-endian byte length. Concatenate in that order.
4. Calculate SHA-256 with the pinned `@noble/hashes` implementation.
5. Interpret digest bytes 0–15 as four unsigned 32-bit little-endian xoshiro state words. If all four are zero, replace the fourth with `0x9e3779b9`.
6. Advance xoshiro128** eight times as warm-up and discard those values.
7. `uniform` returns the next unsigned 32-bit output divided by `2^32`.
8. `integer` uses rejection sampling rather than modulo, so every integer has equal probability.
9. `triangular` applies the standard inverse triangular CDF to one `uniform` draw and validates `min ≤ mode ≤ max`.
10. `weighted` sorts string candidates by code-point order, sums finite nonnegative weights, multiplies one uniform draw by the total, and selects the first cumulative interval strictly greater than the draw.
11. `shuffle` uses a single local generator after warm-up and an unbiased Fisher–Yates shuffle from the final index down to one.

The exact xoshiro128** transition and output function follow the algorithm authors' published reference implementation and are copied into `RandomOracleV1` with attribution. The golden vectors freeze any JavaScript unsigned-shift or endianness details which prose could leave ambiguous.

Requirements:

- Golden test vectors for at least 100 seeds/keys.
- Algorithm version stored in the save.
- A future `V2` never changes a `V1` run.
- All weighted selection sorts candidate IDs stably before applying weights.
- Invalid negative, non-finite, or all-zero weights fail validation.
- Helpers consume a documented number of local draws.

Keyed random access is preferable to one mutable global stream because adding a decorative event or new rival check cannot perturb model alignment or the ending.

### 10.3 Event option precommitment

At event instantiation, derive a hidden root key from run seed, event instance ID, event definition ID, and definition version. Each option/check uses a child key. The instance stores the root key version and any results which must survive rule-version changes.

Post-run audit records include key, draw, threshold, visible inputs, hidden inputs, and result for designated major checks.

### 11.2 Modifiers

Temporary and permanent bonuses use a common record:

```ts

  id: ModifierId;
  source: EffectSource;
  target: ModifierTarget;
```

`ModifierTarget` is a closed, typed set such as:

```text

lab.fundraising.offerCash
model.incident.hazard
researcher.recruitment.strength
```

The content compiler rejects unknown targets. Modifier order is `min/max constraints`, then additive base changes, then multiplicative changes, then final clamps, unless the target definition explicitly says otherwise. Tooltips request a `ModifierBreakdown` from the same resolver.

Leader bonuses are modifiers: Dennis Hassabi's bonus targets `lab.research.all.output` with `multiply 1.20`; Liang Wenfang's targets `lab.compute.workloadThroughput` with `multiply 1.20`. Throughput modifiers never alter `GpuLotState.physicalCount` or the number shown as GPUs.

### 11.3 Predicates

Content prerequisites are an abstract syntax tree, not string expressions:

```ts

  | { type: "all"; items: Predicate[] }
```

The `MetricRegistry` defines how each allowed metric reads state and whether it is legal in player-visible preview copy. Authored data cannot traverse arbitrary object paths.

### 11.4 Checks

```ts
interface CheckDefinition {
  id: string;
  strength: ScoreExpression;
  difficulty: ScoreExpression;
  minimumProbability: number;
  maximumProbability: number;
  randomKeySuffix: string;

```

`ScoreExpression` is a validated arithmetic tree over registered metrics and constants. It supports addition, subtraction, weighted sum, min, max, clamp, and named formulas. It does not support loops or arbitrary functions.

The standard logistic implementation is shared by event previews, recruitment, politics, and endgame resolution. There must be exactly one implementation of the GDD formula.

### 12.3 Compiler pipeline

`pnpm content:build` performs:

1. Discover files under declared content roots.
2. Parse YAML with filename and line/column metadata.
3. Validate each record against its Zod schema.
4. Reject duplicate IDs and unsupported definition versions.
5. Resolve all referenced IDs and asset paths.
6. Generate reverse indexes and tag indexes.
7. Validate research prerequisite graph and reject cycles unless explicitly marked as a multi-route group.
8. Validate event predicates, metric keys, effect targets, token names, option availability, cooldown groups, and delayed follow-ups.
9. Verify lab starts, roster exclusivity, leader modifiers, and every required AI family.
10. Verify every localisation key exists in the base language and every placeholder matches its message schema.
11. Run semantic balance checks such as fraction sums, min/max ordering, nonnegative costs, reachable thresholds, and stable IDs.
12. Sort definitions by ID, emit `content.bundle.json`, generated TypeScript indexes, JSON Schema for editor support, and a content report.
13. Hash the canonical output and store the hash in the manifest.

The release build fails on warnings classified as `release-blocking`, including a real paper without a source link, a portrait without alt text, an event branch with no reachable state, or a catastrophic effect missing the required safety gate.

#### 18.2.3 Rival candidate countdown

When a rival-owned model meets the canonical candidate criteria,
`advanceRivalCandidateCountdowns` creates one hidden countdown with a 26-week base. Safety
commitment, race urgency, political process, recent contained incidents, and an active shared-safety
standard contribute an immutable duration breakdown captured at countdown start. No term compares
the rival with the player's hidden or visible progress.

`projectRivalCandidateCountdowns` returns only an estimated week range, qualitative confidence, and
urgency. Its error radius shrinks with the caller's intelligence rating; `completesAt`, the exact
duration breakdown, and the stored noise unit remain canonical audit state. Starting a countdown
emits a public candidate signal, requests the `race-emergency` auto-pause, and activates the
`rival-candidate` mandatory event detector. Crossing the last thirteen weeks requests a separate
`rival-final-year` auto-pause (presented to the player as **Rival Deployment Imminent**).

A rival has no calendar backstop or emergency-candidate shortcut. Its hidden deployment countdown
starts only after that rival completes all four Candidate Programme works and a specific model clears
Frontier Capability 88+ with every capability at 80+. If that qualifying countdown completes before
the player reaches a terminal ending, the engine resolves the canonical
`base:ending.rival-ascendance` loss. This path never performs a catastrophe check and never uses an
extinction ending.

#### 18.2.4 Rival model and compute operations

The weekly rival policy has two layers. Strategic commands adjust GPU allocation and research focus
through the next-tick order queue. At most one operational command per rival per week then uses the
same validated purchase, training, productisation, and deployment rules as the player. There is no
parallel rival-only model-growth formula.

Operational priorities are deliberately sequential: finish productising a trained successor, deploy
that successor according to the lab personality, start a due successor training run, then fill a
phase-dependent compute target. Dataset policy, training-safety protocol, productisation mode, and
deployment policy are derived from the persisted personality and current strategic plan. Every
issued command is recorded in `RivalStrategyState.weeklyCommands`; rejected commands are engine
errors and balance-runner anomalies rather than silent skips.

Rival finance follows the GDD's reduced Cash Stability model. Rivals still accrue market revenue and
pay real operating, training, and compute entries, but they do not run the player's interactive
fundraising mini-game. At each quarter boundary, a player-independent function of scientific
prestige and commercial appetite restores a small operating floor; a separate reserve capped at 2%
of the rival's current market value can support growth. GPU orders are never financed to their exact
shortfall, so a rival can have the capacity and ambition to scale while still lacking the capital.
Every grant remains an ordinary auditable finance-ledger entry and is not based on the player's cash,
research, or race position.

Rival campuses are off-screen but not pre-built. A weekly infrastructure system traverses the same
authored facility prerequisites and construction durations as the player, beginning each tier only
when that tier unlocks. Completed data-centre facilities set the physical GPU ceiling used by the
normal GPU market. At capacity, rivals retain the automatic refresh policy, but it must sell
unreserved old hardware, wait through the monthly ordering cadence, afford the replacement, and wait
for the ordinary delivery lead time before the new hardware is usable. Candidate Programme works
likewise require their exact prerequisite facility, level-70 relevant research, and enough real fleet
throughput before construction may begin.

Candidate detection examines every completed model owned by the rival, not only its current
commercial model. A frontier successor can therefore begin the hidden countdown while it is still
internal or being productised. Once started, the countdown remains attached to that exact model so a
later shutdown or deployment-policy change pauses or resumes the existing clock instead of silently
substituting a different model.

#### 18.2.5 Global race phases and hardware eras

Ordinary play advances monotonically through Foundation, Scaling, and Frontier from the highest true
Frontier Capability of any completed world model. FC 30 opens Scaling, matching the product-model
scaling-wave trigger, and FC 65 opens Frontier. At most one phase transition occurs in a week, so an
unusually strong model cannot skip the intermediate unlock surface. Crisis remains owned exclusively
by the endgame state machine.

GPU generations unlock independently when the highest true Frontier Capability of any completed
world model reaches their authored `unlockAtWorldFrontierCapability`. Unlocking changes
`world.currentGpuGenerationId` for new offers and training-era comparisons; it never rewrites
existing lots. Both phase and hardware transitions emit typed domain events and append player-safe
narrative audit entries.

but not the candidate's hidden truth or exact completion date. Rival research and countdowns continue
during the player's Deployment Crisis, so entering final review does not suspend the race.

## 24. Persistence, saves, migrations, and replay

### 24.1 Save envelope

```ts
interface SaveEnvelopeV1 {
  format: "neolab-save";
  saveVersion: number;
  engineRulesVersion: string;
  contentVersion: string;
  contentHash: string;
  randomContractVersion: number;
  saveId: string;
  slotType: "autosave" | "manual" | "crisis-checkpoint";
  displayName: string;
  createdAtIso: string;
  updatedAtIso: string;
  checksum: string;
  state: unknown;
  commandLog?: unknown;
}
```

Real timestamps are envelope metadata and do not affect the run. `state` is parsed through version-specific schemas, migrated, then validated before use.

The checksum detects accidental corruption; it is not anti-cheat or cryptographic authentication.

### 24.2 SaveRepository

```ts
interface SaveRepository {
  list(): Promise<SaveMetadata[]>;
  load(saveId: string): Promise<LoadSaveResult>;
  write(request: WriteSaveRequest): Promise<SaveMetadata>;
  delete(saveId: string): Promise<void>;
  export(saveId: string): Promise<Blob>;
  import(file: Blob): Promise<ImportSaveResult>;
}
```

`IndexedDbSaveRepository` is the production implementation. `MemorySaveRepository` supports tests and component stories. The runtime knows only the interface.

### 24.3 Save policy

- One rotating autosave, written at cycle boundaries and after major project completions
- Immediate autosave before and after critical event resolution
- One protected Crisis Start checkpoint per run
- Several user-named manual saves
- JSON export/import
- Settings stored separately from run state

Writes are atomic at the repository level: write new record, verify, then update slot pointer. A failed write leaves the previous autosave intact.

### 24.4 Migrations

```ts
interface SaveMigration<From, To> {
  fromVersion: number;
  toVersion: number;
  migrate(input: From, context: MigrationContext): To;
}
```

Migrations are pure, sequential, fixture-tested functions. They may use content ID aliases from the manifest. They never draw randomness; if new state needs a seeded value, it is derived from the run seed and a stable migration key.

Every release keeps representative saves from previous public versions and proves they load. If a save cannot be migrated safely, the UI explains why and preserves the original export.

### 24.5 Content compatibility

On load:

1. Validate envelope and checksum.
2. Migrate save schema.
3. Resolve content aliases.
4. Verify all referenced mechanical definitions exist.
5. For unresolved event instances, load their snapshotted mechanical version or run an event migration.
6. Validate global invariants.
7. Reproject player view.

Copy and art can update freely. Removing a mechanical content definition referenced by saves is a breaking change requiring alias, tombstone definition, or migration.

### 24.6 Command log and replay

Development and shareable-seed builds can store:

```ts
interface LoggedCommand {
  sequence: number;
  tick: Tick;
  command: GameCommand;
  resultingStateHash: string;
}
```

A replay creates the initial state, advances ticks, applies commands at recorded ticks, and compares hashes. Clock speed and screen navigation are absent. Production saves may omit old low-value command entries to reduce size, but the decision log and major audit checks remain.

### 24.7 Local high scores and future online leaderboard

Launch uses an `IndexedDbHighScoreRepository` with two local boards: all completed runs and winning
runs. Each retains the best 50 entries and stores run ID, lab, leader, ending, seed, difficulty,
score version, raw and adjusted score, category totals, total ticks, content hash, and engine
version. Deleting a save does not silently delete its high-score summary; the high-score screen has
its own explicit delete action.

```ts
interface HighScoreRepository {
  list(board: "all-finished-runs" | "winning-runs"): Promise<HighScoreEntry[]>;
  record(entry: HighScoreEntry): Promise<void>;
  delete(runId: RunId): Promise<void>;
}

interface LeaderboardSubmissionV1 {
  runId: RunId;
  playerAlias: string;
  seed: Seed128;

```

The first static build has no global board. Client-side numbers can be edited and GitHub Pages

Email, save slots, machine identifiers, and free-text local notes are not part of the protocol.

### 24.8 Developer save inspector

`pnpm save:inspect -- SAVE.json` runs the exact production envelope/checksum/migration/schema/invariant
pipeline, then prints a stable summary of run identity, versions, state hash, economy, research,
entity counts, model truth, endgame, and score. Supplying two files compares their migrated canonical
states by deterministic JSON Pointer path; `--max-changes` bounds returned rows while retaining the
full count. `--json` and `--output` produce machine-readable format-1 evidence.

The CLI rejects files above the browser import limit before reading them and never modifies source
saves. Its JSON is explicitly privileged and may include seeds, hidden safety, and hidden
institutional state; it is developer-only, has no network path, and is absent from the web bundle.

## 25. Testing strategy

### 25.1 Test layers

| Layer | Tool | Purpose |
|---|---|---|
| Formula unit tests | Vitest | Exact equations, boundaries, breakdowns |
| System tests | Vitest | One command or tick phase over scenario state |
| Invariant/property loops | Vitest + testkit | Thousands of generated allocations and states |
| Scenario tests | Vitest | Multi-week economic, paper, incident, and crisis stories |
| Replay/golden tests | Vitest | Determinism across seeds and command logs |
| Content tests | Compiler + Vitest | Schema, references, reachability, source and token checks |
| Component tests | Vitest Browser/Testing Library | Accessible interaction and view rendering |
| End-to-end tests | Playwright | New game through ending across browser engines |
| Visual tests | Playwright screenshots | Intentional layout/art regression at fixed viewports |
| Balance simulations | balance-runner | Distribution and strategy health, not pass/fail unit behaviour |

### 25.2 Testkit

The testkit exposes builders with safe defaults:

```ts
const state = scenario()
  .atTick(520)
  .withPlayerLab(lab => lab
    .cash(42)
    .gpus("gpu.kepler", 40_000)
    .rating("safetyCulture", 70))
  .withModel(model => model
    .fc(90)
    .access(4)
    .hiddenSafety({ alignment: 55, corrigibility: 40 }))
  .build();
```

Builders validate on `build`. Tests which need impossible state must opt into `unsafeFixture()` and state why.

### 25.3 Required golden tests

- RandomOracle vectors
- New-game baseline for all five leaders and four difficulties
- First 100 ticks of a no-command seed
- A representative paper race and diffusion chain
- A training run with every scale and safety protocol
- Weak versus strong evaluation observation distributions
- Every fair-catastrophe precondition boundary
- Rival candidate countdown
- Each Deployment Crisis stage and resolution gate
- Save migrations and replay hashes

### 25.4 Invariant campaigns

CI runs short invariant campaigns; nightly or pre-release jobs run long campaigns.

`pnpm invariant:smoke` executes 240 deterministic `random-legal` runs across up to 62,400 ticks;
`pnpm invariant:long` expands that to 400 runs across up to 208,000 ticks. Both use the
production command validator and transition path, whose every commit runs the global invariant
pack. The report records actual committed ticks because terminal runs stop early. Every player
projection is scanned for forbidden hidden keys, every run is replayed to its terminal hash, and
the stable JSON report fails on structural anomaly counters or any catastrophe record that was not
legally gated. CI retains the short report as private build evidence.

Generate legal random commands across thousands of ticks and assert:

- No crash, NaN, orphan, over-allocation, or impossible event
- Finance ledger reconciliation
- Catastrophe legality
- Stable event option availability
- Endings eventually terminate when forced conditions exist
- Hidden keys never enter normal player views

### 25.5 Content branch coverage

The compiler emits every event option and outcome branch. `pnpm content:branches` uses the real
compiled catalogue and simulation to produce
`artifacts/content/event-branch-coverage.json`. For each option it constructs a legal witness from
the closed predicate metrics, flags, phase, and declared known costs. Disabled legacy coalition
effects receive a dedicated compile-only fixture and cannot become player-reachable. A deterministic
test oracle controls only the already-authored outcome interval, then the harness instantiates the
real event, round-trips the unresolved instance
through the production save loader, resolves the real option and effects, and commits all simulation
invariants. Every option and outcome receives a stable covered/uncovered record and terminal state
hash.

An empty draft catalogue reports `empty`, never `complete`. Any non-empty uncovered branch makes the
command fail. Direct catastrophe effects are already rejected statically; forced resolution plus
the invariant pack also fails if any future handler creates an illegal catastrophe record. There is
deliberately no silent `manual-only` escape hatch: a genuinely unconstructable branch must first gain
a named dedicated fixture and reviewed registry contract.

### 25.6 UI and accessibility tests

- Keyboard-select every leader, open dossier, compare, and confirm
- Operate all allocation sliders without pointer
- Preserve focus when event overlays open and return it on close
- Prevent background interaction behind critical modal
- Render resource warnings without colour dependency
- Verify accessible names do not contain hidden safety truth
- Verify reduced motion removes nonessential campus and celebration animation
- Test minimum laptop viewport, 200% zoom, and long text expansion

### 25.7 Coverage policy

Aim for branch coverage above 90% in `packages/sim` and 80% in content handlers and critical UI flows. Coverage is a backstop, not a substitute for scenario and invariant tests. Generated content bundles and art are excluded.

## 26. Balance runner

### 26.1 Headless API

```ts
interface SimulationPolicy {
  id: string;
  decide(view: PolicyView, available: AvailableCommandView[]): GameCommand[];
}

interface BalanceRunRequest {
  seeds: Seed128[];
  difficultyIds: ContentId[];
  leaderIds: ContentId[];
  mandateIds: ContentId[];
  policies: SimulationPolicy[];
  maxTicks: number;
  traceSampleRate: number;
  matrixMode?: "paired" | "cartesian";
  shard?: { index: number; count: number };
}

function runBalanceBatch(request: BalanceRunRequest): Promise<BalanceReport>;
```

Policies see a restricted `PolicyView` comparable to player information. A privileged diagnostic policy can exist but must be labelled.

### 26.2 Initial policies

- Balanced generalist
- Capability-first
- Commercial compounder
- Open-science prestige
- Safety/institution-first
- Secretive proprietary lead
- Random legal baseline
- Intentionally bad baselines such as `never-fund-serving` and `never-train-model`

Scripted policies are not expected to play like experts. They expose dominant formulas, dead economies, and unreachable paths.

### 26.3 Reports

Export machine-readable JSON plus CSV summaries for:

- Win funnel and ending distribution
- Calendar and real-time proxy length
- Cash, compute, Aura, RP, safety evidence, and capability curves
- World-first papers by lab and phase
- Researcher hiring, departure, and slot utilisation
- Facility timing and return on investment
- Event frequency, option selection, success calibration, and delayed follow-up rate
- Rival competitiveness and countdown windows
- Endgame factor distributions and gate results
- Results by leader, mandate, difficulty, policy, and seed

The report flags but does not automatically “fix” deviations from GDD targets.

### 26.4 Constant sweeps

Balance constants have stable keys. The implemented allowlist is `economy.startingCash`,
`economy.startingOwnedGpus`, `economy.fundingClimate`, `research.baseRpCoefficient`,
`research.teraflopScaleDivisor`, and `facilities.baselineOwnedGpuCapacity`. The runner can override one
without rebuilding content and sweep a range. An event-rate key must be added when opportunity-rate
constants move out of engine code; until then the tool must report that calibration gap rather than
pretend to override it. Release builds do not expose arbitrary override controls.

### 26.5 Implemented runner and release matrix

`@neolab/balance-runner` sends every command through `validateCommand`/`applyCommand` and every week
through `advanceOneTick`. All ten section 26.2 policies are implemented. Policies see only the
player-safe `GameView` plus validated command descriptions; canonical state is reserved for
post-decision diagnostics.

The balanced generalist probe must exercise the allocation controls a competent player would
actually use. Its opening posture serves 62.5% of the fleet, sends 60% of the remaining GPUs to
capabilities and 40% to safety, and assigns non-zero capability weight to all eight visible
programmes. This is harness policy, not a simulation balance constant: the authored launch state
remains the deliberately narrow 2012 portfolio, other policies retain distinct postures, and the
probe reads neither hidden paper breakthrough levels nor rival state. A structural fixture locks the
complete 10,000-basis-point domain portfolio and a long seeded regression locks the coarse 20–70%
paper-race band.

The API has two explicit matrix modes. `paired` rotates leader, mandate, and difficulty over
seed/policy pairs for cheap smoke runs. `cartesian` expands every seed × difficulty × leader ×
mandate × policy configuration. Each configuration has a stable ordinal and semantic run key; shard
`i/n` owns ordinals where `ordinal % n === i`. Aggregation reconstructs every summary from raw runs
and rejects missing/repeated shards, content or configuration drift, duplicate keys, and ordinal
gaps.

`pnpm balance:smoke` runs 30 two-year paired probes. `pnpm balance:horizon` runs every policy for up
to 1,120 weeks against one seed, samples deterministic replay, and observes whether rivals naturally
complete the Candidate Programme, train qualifying models, and resolve their countdowns. `pnpm balance:endings` runs
ten seeds across the seven viable core strategies for 70 full-horizon ending calibrations; the
deliberately broken baseline policies are excluded. `pnpm balance:full` runs 1,000 ten-year paired
probes.
`pnpm balance:release` defines the 10,200-run release matrix: 17 seeds × four difficulties × five
leaders × three mandates × ten policies. The scheduled workflow executes the horizon probe plus ten
1,020-run matrix shards and retains the horizon and rebuilt aggregate artifacts for 90 days. The
ten-year Cartesian cap is a throughput cohort, not late-game evidence; targets without a qualifying
horizon or matrix sample remain unavailable.

Report format 2 includes the complete GDD section 48 funnel and loss families; calendar and explicit
real-time proxy; sampled resource curves; paper ownership; researcher turnover and slot use;
facility timing and a labelled, confounded 26-week cash-delta diagnostic; event option/outcome and
follow-up metrics; hidden-evidence calibration; rival plans/windows; endgame stages/gates; and
structural anomaly counters. Flat CSV files cover runs, policies, dimensions, targets, resources,
facilities, and events. Each sampled run stores its exact command log and terminal state hash; the
CLI replays it without the policy and fails on any mismatch.

Rival plausibility is sampled at the first canonical transition into Frontier. A run which ends
earlier carries a labelled run-end fallback for diagnosis, but that fallback is excluded from the
GDD section 48.7 target and policy-rate denominators. The leading response window is independently
captured when the first live rival candidate countdown appears, so a completed Rival Ascendance
does not retroactively turn an initially viable window into zero weeks.

Target rows use `pass`, `fail`, or `unavailable`. Missing content or a promise with no resolved trial
is never coerced to zero. Event checks may carry a typed qualitative label and explicit success
outcome IDs; the runner aggregates trials/successes for every label and tests “Very likely” against
85–100%, without parsing probability semantics from prose. Target misses never edit constants or
fail CI. Engine exceptions, replay mismatch, incomplete matrices, and structural corruption do
fail.

The allowlisted sweep API clones compiled content in memory and changes one stable key over identical
seeds. It records the base content hash and one full report per value; it never writes the accepted
value back. The protocol and proxy definitions are documented in `docs/balance-validation.md` and
`tools/balance-runner/README.md`.

The original Stage 6 1,000-run batch took 624.7 seconds and exposed universal insolvency. Canonical
phase progression, calendar-driven GPU eras, and rival compute/model operations now exist and use the
ordinary production rules. A funded long-horizon diagnostic reaches Scaling, Frontier, and the Rubin
era with several rival model generations; the two-year smoke cohort still exposes early insolvency,
an incomplete authored event catalogue, and too few natural endgame samples. These are
simulation/content/balance findings, not reasons to falsify a green runner result. Rival plausibility
retains a labelled run-end race-strength fallback for runs which never reach Frontier, but only
first-Frontier snapshots enter the GDD section 48.7 target.

### 26.6 Human playtest evidence

`@neolab/playtest-tools` validates versioned JSON session records separately from headless balance
results. A record identifies the exact commit and content hash, uses a non-identifying participant
pseudonym, requires explicit notes consent and exclusion of personal data, and captures environment,
run duration/result, fairness, crisis-earned rating, decision times, dominant UI habits, humour
observations, and categorised remediation issues.

The seven GDD section 49.6 questions are a closed ID registry. Completed sessions must contain each
question exactly once and may not use `not-asked`; evidence records whether the answer was obtained
without a leading prompt. Two or more `partial`/`unclear` results for one question form a repeated
comprehension failure for triage.

`pnpm playtest:report` writes a deterministic evidence report without claiming success. The stricter
`pnpm playtest:gate` defaults to five completed sessions on one commit/content hash, requires every
answer clear and every issue resolved, and still returns only `ready-for-manual-review`. Human sign-off
is required to check S9.7. Drafts and the blank template do not count; historical evidence is never
rewritten after a fix.

- Ordinary weekly tick: p95 under 4 ms
- Cycle/quarter tick: p95 under 8 ms
- Worst normal completion tick: under 16 ms
- Player-view projection: p95 under 6 ms
- Save serialization: under 100 ms for a mature run
- 10,000 headless normal runs: practical as a CI/nightly batch, parallelised in worker threads or processes

Measure before adding a Web Worker to the browser. If normal ticks exceed budget, move `sim` behind a worker adapter without changing public commands/views. The first implementation remains on the main thread for simpler debugging.

### 27.2 UI

- Avoid subscribing large dashboard regions to the entire `GameView`.
- Virtualise archive and event lists only when measured list size justifies it.
- Memoise expensive SVG chart geometry by view version.
- Decode portrait atlases ahead of the screen which uses them.
- Campus animation targets 60 fps but may drop decorative updates to 30 fps.
- A critical dialog must open immediately even while art loads.

### 27.3 State size

Target mature save JSON under 5 MB uncompressed. Prune redundant feed prose by storing template key and tokens where possible. Keep the full decision log and major audit records. Never prune state required for future consequences.

## 28. Diagnostics and developer tools

Development builds include a toggleable inspector outside the normal player UI:

- Current tick phase and system timings
- Command validation and last transition audit
- Finance ledger
- Modifier breakdown by target
- Random key lookup and golden value
- Paper thresholds and progress
- Hidden model safety and evaluation error
- Event eligibility and weights
- Rival plan utilities
- Endgame gate inputs
- Invariant runner
- Export current scenario as a test fixture

The inspector imports privileged APIs from `@neolab/sim/debug`, a package export omitted from the production bundle through build conditions. Do not hide it only with CSS.

The implemented browser boundary uses a development-only dynamic import guarded by
`import.meta.env.DEV`. `BrowserGameRuntime` exposes canonical state only when its explicit
development option was enabled at construction, while the normal runtime snapshot remains the
player-safe `GameView`. Per-system durations are collected through an injected monotonic timing
observer and never enter canonical state or replay. The inspector exports deterministic
`neolab-developer-scenario-v1` fixtures containing the content hash and invariant expectations.
A release-audit sentinel scan fails if the privileged projection reaches emitted HTML, JavaScript,
or CSS, proving exclusion rather than relying on a hidden DOM node. Operational instructions live
in `docs/developer-inspector.md`.

### 28.1 Logging

Simulation logs are structured records, not freeform console messages:

```ts
interface DiagnosticRecord {
  level: "debug" | "info" | "warning" | "error";
  code: string;
  tick?: Tick;
  systemId?: SystemId;
  entityRefs?: EntityRef[];
  data: Record<string, JsonValue>;
}
```

Player-facing errors map stable codes to useful copy. Production does not send logs off-device without explicit telemetry consent.

## 29. Extensibility cookbook

### 29.1 Add an event

1. Add one YAML definition and localisation messages.
2. Use existing predicates, checks, effects, and token bindings.
3. Add portrait/card assets if needed.
4. Run the content compiler.
5. Add fixtures for unusual branches; generic schema/reachability tests cover the rest.
6. Run event-frequency balance tests.

No React or simulation change is needed if existing effect vocabulary is sufficient.

### 29.2 Add a star researcher

1. Add definition, portrait, alt text, source notes, skills, values, traits, and event hooks.
2. Add localisation biography and reactions.
3. Add roster-pool tags and any relationship affinities.
4. Compile and run talent-market composition tests.

No subclass or component is created. Generic portrait cards and dossier screens render the definition.

### 29.3 Add a paper

1. Add educational metadata, authoritative link, domain weights, prerequisites, effort, unlock effects, Aura, and diffusion.
2. Add any new generic recipe/unlock definitions.
3. Compile to validate graph reachability and cycles.
4. Add a scenario test if the paper introduces an alternative route or unusual diffusion.

### 29.4 Add a leader and lab

1. Add leader and lab definitions, modifiers, biographies, source notes, art, palette, AI family, starting roster rules, and rival personality.
2. Add lab-specific event copy variants and voice guide.
3. The leader-selection screen discovers the new definition automatically.
4. Add new-game golden fixture and balance matrix row.

Hard-coded assumptions that exactly five labs exist are forbidden outside first-release content tests.

### 29.5 Add a facility or upgrade

1. Add cost, duration, prerequisites, capacity, modifiers, operating expense, art states, and campus slot tags.
2. Use the generic construction handler.
3. If it unlocks a new project, add that project definition separately.
4. Add return-on-investment and capacity boundary tests.

### 29.6 Add a new authored effect

Only when existing effects cannot express the mechanic:

1. Write the player-facing rule in the GDD.
2. Add a discriminated `Effect` type and Zod schema.
3. Add executor logic, audit representation, preview representation, and `assertNever` updates.
4. Decide save and delayed-effect migration behaviour.
5. Add unit, content, and branch tests.
6. Document the effect for content authors.

### 29.7 Add a new major mechanic

A new mechanic requires an explicit vertical slice through architecture:

1. Canonical state slice or entities
2. Commands and validation
3. Tick system in a declared phase
4. Content definitions and compiler rules
5. Effects/modifier targets/metrics only where needed
6. Player-safe selectors and view types
7. React feature UI
8. Save schema and migration
9. Scenario, replay, invariant, and E2E tests
10. Balance policy/report fields
11. GDD and technical-document updates

This checklist prevents “small mechanics” from becoming untracked state mutated from a component.

### 29.8 Future content packs

The internal compiler may support multiple ordered packs:

```text
base → official-expansion-1 → scenario-overrides
```

Packs can add definitions and localisation or explicitly override balance keys permitted by their manifest. They cannot execute JavaScript. Public user-mod loading is postponed until content security, version compatibility, asset limits, and support expectations are designed.

## 30. Security, privacy, accessibility, and legal metadata

### 30.1 Browser security

- No `eval`, `new Function`, executable content scripts, or arbitrary HTML from YAML/saves.
- Parse imports as `unknown` with size limits before Zod validation.
- Escape plain text and render rich text through a closed component AST.
- External paper/source links use `https`, open with `noopener,noreferrer`, and display the destination domain.
- Configure a Content Security Policy for static assets.
- Do not embed private API keys; there is no required backend.
- Limit imported save size and entity counts to prevent resource exhaustion.
- Never use the deterministic PRNG for security tokens.

### 30.2 Privacy

- Game is fully playable without account or telemetry.
- Save data remains local unless the player exports it.
- Configured production builds automatically use documented, cookie-free Hosted Umami analytics.
  There is no in-game analytics opt-out; builds without a Hosted Umami site ID, local development,
  and developer endgame scenarios remain hard-disabled.
- Analytics contain no save text, run seeds, hidden model traits, real-person interaction history,
  raw exception messages, or raw stack traces. Sanitized crash fingerprints use the same control.

### 30.3 Accessibility

- Semantic HTML owns all dashboard interaction; canvas remains decorative or has a DOM alternative.
- Full keyboard navigation and visible focus.
- Slider values announced with percent and physical GPUs/week; generation mix is available in the accessible description.
- Focus trapping and restoration for modals.
- Colour-blind-safe palettes and redundant icons/text.
- 200% zoom at minimum laptop viewport.
- Reduced motion, animation speed, subtitle, and volume controls.
- Screen-reader projection uses the same uncertainty labels as visible UI and never leaks hidden truth.
- Timed events auto-pause when critical and provide generous non-critical expiry settings.

### 30.4 Real-person and source metadata

Leader, researcher, and paper definitions include structured source notes, last-reviewed date, portrayal status, and legal-review status. Build reports list missing or stale reviews. Legal status is workflow metadata, not a player stat.

## 31. Build, CI, and distribution

### 31.1 Required scripts

```text
pnpm dev                 Start web app and watch content
pnpm build               Compile content, type-check, test, and build static app
pnpm typecheck           TypeScript project references
pnpm lint                ESLint and formatting checks
pnpm test                Vitest unit/integration suite
pnpm test:browser        Browser component tests
pnpm test:e2e            Playwright suite
pnpm content:check       Full content validation and report
pnpm content:branches    Force every compiled event option/outcome; write coverage evidence
pnpm balance:smoke       Small deterministic strategy matrix
pnpm balance:endings     70-run core-strategy ending calibration
pnpm balance:full        Large local/nightly batch
pnpm save:inspect FILE   Validate and summarise exported save
```

`pnpm test:browser` is a separate Vitest Browser Mode lane backed by Playwright Chromium. It mounts
components directly rather than navigating the application, so browser-owned semantics such as
focus, `inert`, keyboard events, and DOM cleanup are exercised independently of the Playwright E2E
suite.

`pnpm test:e2e` runs the application contract in Chromium, Firefox, and WebKit. Responsive geometry,
keyboard/accessibility, persistence, economy, research, audio, and world flows run in every engine.
Chromium alone owns pixel snapshots and the CDP CPU-throttled campus profile; those are rendering
and instrumentation contracts rather than cross-engine gameplay exceptions.

### 31.2 CI gates

For every change:

1. Lockfile and package audit sanity
2. Content compile
3. Format/lint
4. Type check
5. Unit, system, scenario, replay, and short invariant tests
6. Web production build
7. Playwright smoke tests in Chromium, Firefox, and WebKit
8. Bundle-size and generated-content diff report

Nightly or pre-release:

- Long invariant campaign
- Full balance matrix
- Complete E2E suite
- Visual screenshots
- Previous-save migration suite
- Broken external source-link report, which warns rather than rewriting historical content automatically

The private `verification-monthly.yml` workflow runs the 400-configuration long invariant
campaign independently of the sharded balance matrix and retains its deterministic report for 90
days. Keeping it separate prevents a balance-shard failure from suppressing invariant evidence and
allows either workload to be dispatched privately on its own.

The same read-only workflow walks every authored YAML source URL, deduplicates it while retaining
file/JSON-Pointer references, refuses local/private destinations, follows a bounded redirect chain,
and records reachable, access-restricted, broken, transient, and unsafe results. Link health is a
warning report rather than an automatic historical-content rewrite or release gate. Normal CI also
runs the package manager's production-only high-severity vulnerability audit after its frozen-lockfile
install.

### 31.3 Static deployment

Vite emits static HTML, JavaScript, CSS, content JSON, and assets. Deploy the same build to a normal static host and itch.io HTML5 packaging. Use relative asset handling compatible with an itch.io subdirectory.

No service worker is required initially; stale cached content and saves are a larger risk than installability. Add an offline/PWA layer only with explicit cache-version tests. A loaded game continues without network because simulation and content are local.

The initial production host is GitHub Pages with a custom GitHub Actions workflow:

1. A protected `main` push runs content checks, type-checking, tests, and a production build.
2. The workflow uploads only the immutable `dist/` artifact, then deploys it to the GitHub Pages environment.
3. Vite receives the correct base path for both the `github.io/neolab.ai/` preview and eventual `play.neolab.ai` custom domain.
4. Hashed JavaScript, CSS, images, and audio receive long-lived cache headers where the host permits; `index.html` and the content manifest must be revalidated.
5. CI rejects a published site above `900 MB`, any single asset above `20 MB`, or a compressed first-load budget above the release target. The initial first-load target is `<= 15 MB`, excluding audio fetched only after player interaction.
6. A tagged release preserves the exact build artifact and content hash for rollback.

No application CPU is provisioned: GitHub Pages serves static files, and each browser owns its simulation runtime. GitHub currently publishes a soft `100 GB/month` bandwidth limit and a `1 GB` site limit. If monitoring approaches the bandwidth limit, deploy the same artifact to Cloudflare Pages and change DNS; do not introduce a backend. Official references: [GitHub Pages overview](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages), [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits), and [itch.io HTML5 uploads](https://itch.io/docs/creators/html5).

## 32. Implementation sequence

No step begins by constructing the entire UI. Build vertical evidence that the rules and boundaries work.

### Milestone 0 — Workspace and contracts

- Create pnpm workspace and packages.
- Add strict TypeScript, lint, test, build, and CI.
- Implement branded IDs/units, Result types, Zod boundaries, and public exports.
- Add architecture dependency checks.
- Add empty compiled-content manifest.

**Exit:** every package builds and forbidden imports fail CI.

### Milestone 1 — Deterministic kernel

- Implement `GameState`, `createNewGame`, transaction, command shell, tick phases, invariants, and RandomOracleV1.
- Implement memory save repository and replay hash.
- Add five leader/lab definitions with exact starting-state golden tests.

**Exit:** same seed/config/commands produce byte-equivalent canonical state.

### Milestone 2 — Ten-minute economy

- Compute capacity/allocation, serving, finance ledger/cycle, one market segment, purchasing, one facility, and runway.
- Minimal React shell with top bar and GPU-allocation sliders.
- Runtime clock and auto-pause.

**Exit:** a player can survive or go bankrupt through legible decisions; forecast reconciles with settlement.

### Milestone 3 — Research and model loop

- Capability domains, safety programmes, paper graph, research progress, publication/public knowledge, training, productisation, and evaluations.
- Ten paper definitions and discovery UI.
- Model/Research workspaces.

**Exit:** a complete seeded paper race and two model generations replay exactly.

### Milestone 4 — People, Aura, and facilities

- General staff, star slots, talent market, offers, morale/loyalty/burnout, promises, departures, Aura, fundraising, and facility catalogue.
- Portrait strip, recruitment screen, campus DOM strip.

**Exit:** at least six stars, five facilities, hiring/poaching/dismissal, and funding event chains work.

### Milestone 5 — Events and politics

- Predicate/effect/check DSL, content compiler reachability, opportunity/mandatory event engine, delayed effects, politics, government crises, and structured decision log.
- Implement 25–35 vertical-slice events.

**Exit:** event outcomes survive save/load, every dynamic name resolves, and no event can illegally cause catastrophe.

### Milestone 6 — Rivals and diplomacy

- Four rival labs, utility policy, paper/model competition, talent moves, market aggregation,
  candidate countdown, relationships, and diplomacy.

**Exit:** headless runs produce credible multi-lab races with no rubber-band cheats.

### Milestone 7 — Complete Deployment Crisis

- State machine, AI channel, crisis projects, pressure collision, final review, deployment modes, all six gates, rollout beats, endings, and post-run audit.

**Exit:** every required victory/loss fixture in GDD section 49.4 is reachable and explainable.

### Milestone 8 — Content-complete alpha

- Five lab voice/leader packages; nine capability tiers; at least 100 papers spanning capability
  and safety; 56 stars; 20 facility families and 44 build/upgrade definitions; 180 ordinary
  events; 30 crisis chains; 600 feed templates; 48 endgame nodes; 12 endgame inserts; four
  prosperity programmes; and 18 ending/epilogue families.
- Legal/source metadata and content review.

**Exit:** no placeholder mechanics or broken content branches; full run median is in target range.

### Milestone 9 — Art, sound, accessibility, and balance

- Final pixel-art test direction, production assets, audio, motion, responsive layout, browser coverage, accessibility audit, and extensive balance/playtesting.
- Decide whether PixiJS is justified from measurements.

**Exit:** GDD balance and accessibility targets pass at release-candidate quality.

### Milestone 10 — Public build

- Save compatibility fixture, release content review, static deployment, itch.io package, optional consented diagnostics, and feedback channel.
- **Automate GitHub Pages deployment:** add `.github/workflows/deploy-pages.yml` using GitHub's official Pages artifact/deploy actions; run content validation, type-checking, tests, and the production Vite build before upload; configure the repository Pages environment and `play.neolab.ai` custom domain; handle both project-site and custom-domain base paths; preserve the content hash and build artifact for rollback; and run a post-deploy smoke test which loads the title screen, starts a seeded game, advances one tick, and verifies static assets resolve without absolute-path failures.

**Exit:** tagged, reproducible build with rollback and archived content hash.

## 33. Public API inventory and completion gate

### 33.1 `@neolab/sim/public`

The web app may import only:

- `createNewGame`
- `loadGameState`
- `validateCommand`
- `applyCommand`
- `advanceOneTick`
- `projectGameView`
- `calculateScoreView`
- Public command types
- `GameView` and child view types
- Save envelope/export types
- Public error and receipt types
- Runtime-neutral formatting metadata

It may not import hidden state, individual system functions, random internals, or privileged audit selectors during an active run.

### 33.2 Concrete runtime classes

The expected stateful classes in the initial browser app are:

- `BrowserGameRuntime implements GameRuntime`
- `AnimationFrameClockDriver implements ClockDriver`
- `IndexedDbSaveRepository implements SaveRepository`
- `BrowserSettingsRepository implements SettingsRepository`
- `WebAudioManager implements AudioManager`
- Optional `PixiCampusRenderer implements CampusRenderer`

Everything else should default to functions, immutable definitions, plain state records, or small adapter interfaces.

### 33.3 Definition of implementation-ready

The project is ready to start code when:

- The GDD's remaining content questions have decisions or named placeholders.
- All balance constants used by the first vertical slice have keys and defaults.
- Five lab/leader definitions are approved enough for implementation.
- The first ten papers, six researchers, three facilities, and 25 events are selected.
- The command, effect, predicate, modifier, project, and endgame unions cover the vertical slice.
- Save version 1 and RandomOracleV1 contracts are frozen.
- The UI flow from leader selection through one event and one model launch is wireframed.

The architecture is complete when a new authored event, paper, researcher, facility, and sixth leader can each be added without editing React component logic or canonical save schemas. A genuinely new mechanic will still require code, but the checklist in section 29.7 makes that change explicit, testable, and migratable rather than magical.
